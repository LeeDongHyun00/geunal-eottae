# M2 시험: 그룹 시나리오, 상태 일치, 초대, 동시 설정, 게이트 지표

[직군별 할 일](../plan.md) 4장의 M2 QA·보안 일입니다. 시험 종류, 결함 등급, 머지 규칙은 [QA](../qa.md)를 따르고, 보안 쪽 시험은 [위협 모델](../security/threat-model.md) 3.4·3.5·5장에 있습니다. 형식은 [M1 시험](m1.md)과 같습니다.

## 1. 범위와 전제

- **M2의 QA는 넷입니다.** 5명 이상 여러 기기 그룹 시나리오, 상태 불일치 검사(같은 로그면 같은 상태), 초대 흐름, 두 사람이 동시에 그룹 설정 바꾸기. 보안은 초대 코드 남용과 누구나 바꾸는 그룹 메타의 남용을 봅니다(4장).
- **실기기는 iOS로 합니다.** 사용자 환경 때문에 안드로이드는 실기기 확인 없이 코드와 CI까지입니다. 안드로이드의 그룹 흐름은 2장의 코어 시험과 에뮬레이터 계측 시험으로만 확인합니다.
- **자동 시험이 먼저입니다.** 여러 기기의 경쟁과 수렴은 사람이 재현하기 어렵습니다. 코어의 가짜 서버(`core/geunal-sync/src/fake.rs`)와 종단 시험(`make e2e`)이 많은 부분을 맡고, 실기기 시나리오는 그 위에서 화면·알림·초대 링크를 봅니다.
- **시험 이름:** 표의 "있음"은 지금 `main`에 있는 시험이고, ＋는 M2에서 더할 시험입니다. 이름은 각 파트가 자기 관례로 옮깁니다. QA는 M2 게이트 때 m1.md 2.6처럼 이름을 대조합니다.

## 2. 자동 시험

### 2.1 같은 로그면 같은 상태 (코어)

그룹 상태(약속, 날짜 잡기, 투표, 참가자, 그룹 메타, 가용 시간 합치기)는 로그와 상태 블롭에서 계산합니다. 두 기기가 같은 순번까지 처리했다면 화면에 보이는 상태가 같아야 합니다.

| # | 확인하는 것 | 시험 | 비고 |
| --- | --- | --- | --- |
| S1 | 같은 로그를 두 번 따로 계산하면 같은 상태 | `the same log derives the same state on two independent runs` | 있음. 속성 시험(`geunal-domain/tests/properties.rs`) |
| S2 | 강퇴와 재가입을 거친 세 기기가 같은 상태 | `three devices derive the same state after a kick and a rejoin` | 있음. 가짜 서버 |
| S3 | 10명(계정마다 활성 기기 1대, [공통 계약](../parts/protocol.md) 1장)이 무작위로 엔트리·커밋·상태 블롭을 보내고, 각 기기가 무작위 시점에 따라잡아도 마지막에 모두 같은 상태 | ＋`ten members converge on one state whatever order they catch up in` | 가짜 서버. 씨앗(seed)을 실패 메시지에 남김 |
| S4 | 처음부터 다시 계산한 상태와 엔트리를 하나씩 받으며 계산한 상태가 같음 | ＋`replaying the whole log equals applying it one entry at a time` | 속성 시험 |
| S5 | 새 멤버가 번들과 가입 뒤 로그로 만든 상태가, 날이 지나지 않은 약속에 대해 오래된 멤버의 상태와 같음 | ＋`a newcomer and an old member agree on live appointments after the bundle` | 번들의 신뢰 범위는 위협 모델 3.4 |
| S6 | 게이트웨이·푸시로 순번이 건너뛰어도 빈틈을 채운 뒤 같은 상태 | `fetches the gap when a pushed seq skips ahead` | 있음 |
| S7 | 같은 공유 상태면 같은 상태 요약값, 다르면 다른 요약값. 요약값은 4.1의 공유 상태만 담음(지난 약속은 가입 시점에 따라 다를 수 있어 뺌) | ＋`two devices with the same shared state show the same state digest` | 6장 1번 결정에 따름. 실기기 비교(3.3)에 씀 |

### 2.2 초대와 가입 (백엔드, 코어)

| # | 확인하는 것 | 시험 | 비고 |
| --- | --- | --- | --- |
| I1 | 초대 코드는 50비트 이상이고 만료가 지나면 거절 | ＋API `refuses an invite code after it expires` | `group_invites.expires_at` |
| I2 | 사용 횟수(`max_uses`)를 넘으면 거절. 두 요청이 마지막 한 자리를 동시에 쓰면 하나만 됨 | ＋API `refuses an invite code past max_uses, even for two joins at once` | |
| I3 | 코드를 만든 멤버나 방장이 코드를 거두면 그 뒤로 거절 | ＋API `refuses an invite code once it is revoked` | 거두기 API는 6장 3번 결정 |
| I4 | 코드로 참여 요청은 IP당 시간당 10회. 넘으면 429와 `Retry-After` | ＋API `limits invite joins per IP` | [백엔드](../parts/api-server.md) 9장 |
| I5 | 그룹당 20명, 1인당 그룹 20개를 넘는 참여·생성은 거절 | ＋API `refuses a join that would put a group past twenty members`, `refuses a twenty-first group` | [개요](../kickoff.md) 결정 |
| I6 | 강퇴된 계정은 같은 코드로 다시 들어오지 못하고 새로 초대받아야 함 | ＋API `a kicked member cannot rejoin with an old invite code` | 다시 초대한 뒤는 `a removed member invited again can be added again by a commit`(있음) |
| I7 | 서버는 `pending`·`active`인 계정만 추가함 | `refuses an Add commit for a device whose account is not pending in the group` | 있음 |
| I8 | 앱은 사람이 수락한 초대의 Welcome만 받음 | ＋코어 `joins only from a welcome for an invitation this person accepted` | 위협 모델 3.4 검토할 결정. 흐름이 정해지면 이름을 맞춤 |
| I9 | 온라인인 멤버 기기 하나가 `pending`을 추가하고, 둘이 동시에 추가하면 커밋 하나만 받고 다른 기기는 다시 확인한 뒤 그만둠 | ＋코어 `two members adding the same pending person leave exactly one leaf` | 계약 6장 커밋 선점 |
| I10 | 추가할 수 없는 사람(기기 목록 404)을 넣으려는 의도가 그 그룹의 다른 커밋·메시지를 막지 않음 | ＋코어 `an add for someone who cannot be added does not hold up the group's queue` | #167 후속. 게이트 항목 |
| I11 | 앱이 깔리지 않은 기기에서 초대 링크를 열면 설치 뒤 같은 코드로 이어짐 | iOS·안드로이드가 이름을 정함 | 안드로이드는 Install Referrer, iOS는 클립보드를 쓰면 [앱 PR 점검표](../security/app-review.md)의 클립보드 규칙 |

### 2.3 두 사람이 동시에 그룹 설정 바꾸기 (백엔드, 코어)

| # | 확인하는 것 | 시험 | 비고 |
| --- | --- | --- | --- |
| C1 | 같은 버전에서 둘이 쓰면 하나만 저장되고 다른 하나는 409 | `two members writing group_meta from the same version, one wins and one gets 409` | 있음(API) |
| C2 | 409를 받은 기기는 최신 블롭에 자기가 바꾼 항목만 다시 얹음. 서로 다른 항목(이름과 색)을 바꿨으면 둘 다 남음 | ＋코어 `re-applies only my changed fields after a state_conflict on group_meta` | 위협 모델 3.5 |
| C3 | 같은 항목을 둘이 바꾸면 나중에 저장된 값이 남고, 모든 기기에 같은 값과 같은 "마지막으로 바꾼 사람"이 보임 | ＋코어 `the later of two writes to the same field wins on every device` | |
| C4 | epoch가 바뀐 뒤 다시 봉인해도 `changed_by`는 그대로 | ＋코어 `keeps changed_by when re-sealing group_meta after an epoch change` | 위협 모델 3.5 |
| C5 | 다시 봉인을 두 기기가 동시에 해도 내용이 바뀌지 않음 | ＋코어 `two devices re-sealing group_meta for the same epoch keep its content` | |
| C6 | 409가 계속 나도 재시도는 한도가 있고 기다림이 늘어남 | ＋코어 `backs off and gives up after repeated state_conflicts` | 변경 전쟁의 재시도 폭주(3.5) |
| C7 | 같은 그룹에서 설정 바꾸기와 멤버 추가 커밋이 겹쳐도 설정이 사라지지 않음 | ＋코어 `a group_meta write racing an add commit survives the epoch change` | |

### 2.4 멤버 변화 (백엔드, 코어)

| # | 확인하는 것 | 시험 | 비고 |
| --- | --- | --- | --- |
| M1 | 방장이 나가면 가장 오래된 활성 멤버가 방장 | `the longest-standing active member succeeds an owner who leaves` | 있음(API) |

| M4 | 나간 사람의 가용 시간은 모든 기기의 그룹 캘린더에서 사라짐 | ＋코어 `drops a departed member's availability from the group calendar` | |
| M5 | 진행 중인 날짜 잡기의 주도자가 나가면 모든 기기가 같은 규칙으로 처리 | ＋코어 이름은 코어가 정함 | 규칙은 [Rust 코어](../parts/rust-core.md)를 따름 |

### 2.5 종단 (`make e2e`)

로컬 스택(`infra/docker-compose.yml`)에서 `core/geunal-e2e`가 헤드리스 기기로 돌립니다. CI의 `e2e`가 같은 대상을 부릅니다.

| # | 확인하는 것 | 시험 |
| --- | --- | --- |
| E1 | 10명이 기기 하나씩으로 그룹을 만들고 초대 코드로 들어와 모두 `active`가 됨 | ＋`ten members join one group with an invite code` |
| E2 | E1 뒤 날짜 잡기 신청, 수락 셋, 투표 하나를 보내고 10기기가 같은 상태 요약값 | ＋`ten devices agree after a date request, three accepts and a poll` |
| E3 | E1 뒤 두 멤버가 동시에 그룹 이름·색을 바꾸고 모두 같은 값 | ＋`two members change the group name and colour at once and every device agrees` |
| E4 | 한 기기가 내려가 있는 동안 강퇴·추가가 일어나고, 돌아와 따라잡아도 같은 상태 | ＋`a device that was offline through a kick and an add catches up to the same state` |
| E5 | 게이트웨이로 `state`·`membership` 이벤트가 접속 중인 기기에 즉시 감 | ＋`connected devices hear state and membership changes without polling` |
| E6 | E1 뒤 한 멤버가 기기를 바꾸고(교체 티켓, [공통 계약](../parts/protocol.md) 2·13장) 외부 가입으로 돌아와도 모든 기기가 같은 상태 | ＋`a member who replaces their device rejoins and every device agrees` |

## 3. 실기기 시나리오 (사용자)

### 3.1 준비

- TestFlight 빌드 하나를 모두 같은 번호로 받습니다. 빌드 번호와 시각을 적습니다.
- 5명 이상이 각자 기기 1대를 씁니다. 계정마다 활성 기기는 1대라서, 같은 계정으로 두 번째 기기에 로그인하면 기기 교체가 됩니다(3.5의 4번). 한 사람은 앱이 깔리지 않은 상태에서 시작합니다.
- 알파 서버의 API와 게이트웨이가 함께 떠 있어야 합니다.

### 3.2 초대 흐름

| # | 하는 일 | 기대 |
| --- | --- | --- |
| 1 | A가 그룹을 만들고 카카오톡 공유로 초대 링크를 보냄 | 공유 카드에 그룹 이름이 보이고, 코드 자체는 미리보기에 드러나지 않음 |
| 2 | 앱이 있는 B가 링크를 엶 | 앱이 바로 열리고 수락 화면. 수락 전에는 그룹에 들어가지 않음 |
| 3 | 앱이 없는 C가 링크를 엶 | 스토어(TestFlight)로 가고, 설치 뒤 첫 실행에서 같은 그룹의 수락 화면 |
| 4 | 수락 뒤 | 몇 초 안에 그룹에 들어가고, 다른 멤버 기기에도 새 멤버가 보임. A의 기기가 꺼져 있어도 온라인인 다른 멤버가 추가함 |
| 5 | 만료됐거나 거둔 코드로 엶 | 이유를 알려 주는 화면. 그룹에 들어가지 않음 |
| 6 | 강퇴된 사람이 예전 링크를 엶 | 들어가지 못함 |

각 단계의 시각을 적어 둡니다. 첫 수락 속도와 초대 전환 계산(5장)의 검산에 씁니다.

### 3.3 같은 그룹, 같은 화면

| # | 하는 일 | 기대 |
| --- | --- | --- |
| 1 | 각자 개인 일정 몇 개를 넣고 그룹 캘린더의 같은 주를 엶 | 모든 기기에서 날마다 같은 띠·색 단계 |
| 2 | 날짜 잡기를 신청하고 셋이 수락, 한 사람이 투표를 엶 | 모든 기기에서 같은 참가자, 같은 투표 결과 |
| 3 | 그룹 설정의 상태 요약값을 모든 기기에서 봄 | 모두 같은 값. 다르면 스크린숏과 함께 "상태 불일치"로 신고(4장) |
| 4 | 한 기기를 비행기 모드로 두고 2번을 하고, 30분 뒤 켬 | 따라잡은 뒤 3번과 같은 값 |
| 5 | 접속 중인 두 기기에서 한쪽이 수락 | 다른 기기에 1초 안팎으로 보임(실시간) |
| 6 | 앱을 닫은 기기 | 푸시 알림이 오고, 열면 바로 반영 |

### 3.4 두 사람이 동시에 설정 바꾸기

| # | 하는 일 | 기대 |
| --- | --- | --- |
| 1 | 둘이 동시에(신호에 맞춰) 한 사람은 이름, 한 사람은 색을 바꿈 | 둘 다 남고, 모든 기기에 같은 값 |
| 2 | 둘이 동시에 이름을 서로 다르게 바꿈 | 하나만 남고, 모든 기기에 같은 이름과 같은 "마지막으로 바꾼 사람" |

### 3.5 멤버 변화

| # | 하는 일 | 기대 |
| --- | --- | --- |
| 1 | 방장이 그룹을 나감 | 가장 오래된 멤버가 방장이 되고 모든 기기에 같게 보임 |
| 2 | 방장이 한 사람을 강퇴 | 강퇴된 사람의 기기에서 그룹이 읽기 전용이 되거나 사라지고, 이후 일정·설정이 보이지 않음 |
| 3 | 강퇴된 사람을 다시 초대해 들임 | 날이 지나지 않은 약속이 보이고, 3.3의 3번 값이 같음. 강퇴 전후의 지난 약속은 달라도 됨 |
| 4 | 한 사람이 다른 기기로 같은 계정에 로그인해 기기를 바꿈 | 이전 기기는 로그아웃되고, 새 기기에서 날이 지나지 않은 약속과 그룹 설정이 보이며 3.3의 3번 값이 같음 |

## 4. 상태 불일치와 보안 점검

### 4.1 상태 불일치 신고

M2 게이트는 "그룹 상태 불일치 신고 0건"입니다.

- **무엇이 불일치인가:** 같은 그룹의 두 기기가 따라잡기를 마친 뒤(당겨서 새로 고침 후) **공유 상태**가 다르게 보이는 것. 공유 상태는 날이 지나지 않은 약속과 그 참가자, 진행 중인 날짜 잡기와 투표, 그룹 설정, 그룹 캘린더입니다. 따라잡기 전의 지연은 불일치가 아닙니다.
- **지난 약속은 따로 봅니다.** 새 멤버 번들은 날이 지나지 않은 약속만 넘기므로([공통 계약](../parts/protocol.md) 5장), 나중에 들어온 멤버나 기기를 바꾼 멤버에게는 지난 약속이 없을 수 있습니다. 지난 약속은 그 기간에 함께 그룹에 있던 기기끼리만 비교합니다.
- **신고 방법:** 두 기기의 상태 요약값과 화면 스크린숏, 시각, 빌드 번호. 요약값이 같은데 화면이 다르면 앱 결함, 요약값이 다르면 코어 결함으로 나눕니다.
- **등급:** 따라잡은 뒤에도 남는 불일치는 S1입니다. 약속 성사에 직접 영향을 주기 때문입니다.
- **세는 법:** 테스터 신고와 3.3 결과를 합쳐 셉니다. 같은 원인의 신고는 하나로 셉니다.

### 4.2 보안 점검 범위

[위협 모델](../security/threat-model.md) 3.4·3.5의 "확인" 칸과 아래를 M2 게이트 전에 봅니다. 찾은 결함은 [QA](../qa.md) 4장대로 다루고, 공개 문서에는 건수와 고친 뒤의 막는 것만 적습니다.

- **초대 코드:** 길이와 무작위성, 만료·횟수·거두기, IP·계정별 레이트 리밋, 코드가 로그·분석·공유 미리보기에 남는지, 앱이 없는 기기에서 코드를 넘기는 경로(Install Referrer, 클립보드).
- **누구나 바꾸는 그룹 메타:** 쓰기 빈도 한도, 커버·프로필 사진 크기와 형식, 오래된 epoch로 덮어쓰기, 서버가 옛 블롭을 돌려줄 때.
- **그룹 한도:** 그룹당 인원, 1인당 그룹 수, 그룹 만들기 빈도.
- **가입:** 사람이 수락한 초대의 Welcome만 받는지(I8), 새 멤버 번들의 신뢰 범위(위협 모델 3.4).
- **푸시:** 알림에 평문 내용이 실리지 않는지, 기기 토큰이 로그에 남지 않는지.

## 5. M2 게이트 지표 세는 법

**대상:** 실제 친구 그룹 5개. 3장 시나리오용 그룹은 뺍니다.
**자료:** 서버가 보는 메타데이터와 기기가 보내는 퍼널 마커(`POST /groups/{id}/funnel`)만 씁니다. 내용은 쓰지 않습니다([개요](../kickoff.md) 1장).

| 지표 | 기준 | 정의 | 셈 |
| --- | --- | --- | --- |
| 초대 전환 | 50% 이상 | 초대 코드 사용 → 활성 멤버 → 첫 가용 시간 공유 | 코드로 참여를 요청한 계정 중, `active`가 되고 그 그룹에 첫 `availability` 블롭을 올린 계정의 비율 |
| 수락률 | 60% 이상 | 날짜 잡기 중 날이 지나기 전에 1명 이상 수락한 비율 | 퍼널 마커의 신청과 첫 수락으로 셈. 취소된 신청도 분모에 넣고 따로 표시 |
| 첫 수락 속도 | 24시간 이내 | 신청 → 첫 수락의 중위 시간 | 첫 수락이 있는 신청만. 수락 없이 날이 지난 신청 수를 함께 적음 |
| 성사율 | 50% 이상 | 날이 지난 약속 중 참가자 2명 이상이었던 비율 | 날이 지난 약속의 참가자 수 마커로 셈 |
| 상태 불일치 신고 | 0건 | 4.1 | 4.1 |

- **표본이 작습니다.** 그룹 5개라 한 그룹이 20%p입니다. 그룹별 값도 함께 적고, 판단은 기획이 합니다.
- **중단 기준:** 초대 전환이 25% 미만이고 온보딩을 두 번 고친 뒤에도 같으면 [개요](../kickoff.md) 1장대로 기획이 다시 봅니다.
