# QA: 테스트 전략, 결함 등급, 머지 규칙

M0 QA 산출물입니다. [개요](kickoff.md) 8장의 게이트와 각 파트 문서의 테스트 장(Rust 코어 9장, API 11장, 게이트웨이 9장, iOS 9장, 안드로이드 7장, 공통 계약 12장)을 한 자리에 모으고, 누가 어떤 시험을 맡아 CI의 어디에서 돌리는지, 결함을 어떻게 등급 매기는지, 무엇이 녹색이어야 머지하는지를 정합니다. 테스트 코드는 파트가 씁니다. QA는 시험 종류와 시나리오를 정하고, 빈틈을 찾고, 게이트 통과를 판정합니다.

## 1. 원칙

1. **로컬 명령이 CI입니다.** 모든 시험은 `make` 대상이고, CI는 같은 대상을 부릅니다([CLAUDE.md](../CLAUDE.md)). 로컬에서 통과한 명령이 CI에서도 그대로 돕니다.
2. **결정적 로직은 코어에서 시험합니다.** 상태 계산, 투표 집계, 추천은 Rust 코어 하나에 있으므로([개요](kickoff.md) 3장 원칙 2), 가장 많은 테스트가 코어에 있고 앱은 "코어 결과를 그리는지"만 봅니다.
3. **같은 로그는 같은 상태를 냅니다.** 원칙 3을 속성 테스트(proptest)와 종단 시험이 직접 검사합니다. 기기마다 다른 상태가 나오면 그룹 기능 전체가 흔들리므로 가장 높은 등급(2장 S0)입니다.
4. **계약은 벡터로 지킵니다.** 파트 사이의 형식은 `core/vectors/*.json`으로 고정하고, 만든 파트와 검증하는 파트의 CI가 같은 파일을 읽습니다.
5. **실기기는 사람이 봅니다.** 시뮬레이터·에뮬레이터에서 안 되는 것(푸시, 알림 확장 메모리, 기기 캘린더, 결제)은 사용자가 실기기로 확인하고, Claude는 시나리오와 체크리스트를 만듭니다([직군별 할 일](plan.md) 1장).

## 3. 종단 시험 시나리오

`core/geunal-e2e`는 앱 없이 Rust 코어 인스턴스를 클라이언트로 써서 로컬 스택(`infra/docker-compose.yml`)과 통신합니다. 테스트 이름은 영어로 쓰고, 아래 번호를 주석에 남겨 시나리오와 대조할 수 있게 합니다.

### 3.1 M0 게이트: 그룹 하나, 클라이언트 3개

[개요](kickoff.md) 8장 M0 게이트를 단계로 풉니다. A, B, C는 각각 저장소 디렉터리와 `SecretStore`가 다른 코어 인스턴스입니다.

| 단계 | 행동 | 확인 |
| --- | --- | --- |
| 1 | A·B·C가 인증 스텁으로 로그인하고 기기를 등록, 키 패키지 게시 | 각자 `device_id`가 다름 |
| 2 | A가 그룹을 만들고(MLS epoch 0) 초대 코드 발급 | 서버의 멤버 목록에 A만 `active` |
| 3 | B·C가 초대 코드로 참여(`pending`). A가 Add 커밋과 Welcome을 올림 | B·C가 `welcome` 이벤트를 받고 가입, 세 기기의 epoch가 같음 |
| 4 | A가 `Request`, B가 `Response(accept)`, C가 `Response(accept=false)`, A가 `Poll`, B·C가 `PollVote` | 세 기기의 `seq` 커서가 같고, 로그에 빈틈이 없음 |
| 5 | 게이트웨이를 통한 즉시 전달 | 접속 중인 기기는 `entry` 이벤트로 받고, 끊긴 기기는 `GET /groups/{id}/log`로 따라잡아 같은 결과 |
| 6 | A가 C를 강퇴(서버 멤버 상태 변경 → `membership` 이벤트 → B가 Remove 커밋) | epoch가 1 오르고, C는 이후 메시지를 풀 수 없음(`not_member`) |
| 7 | C가 다시 초대 코드로 들어와 Add 커밋으로 가입 | C는 번들(`newcomer_bundle`)로 날이 지나지 않은 약속을 받음 |
| 8 | 세 기기의 상태 함수 출력 비교 | 약속 상태, 참가자, 투표 집계가 바이트 단위로 같음 |
| 9 | 같은 epoch에 A·B가 동시에 커밋 | 하나만 수락, 다른 하나는 409 `epoch_conflict` 뒤 재시도로 수락 |
| 10 | B가 지난 epoch로 메시지 전송 | 409 `stale_epoch` 뒤 다시 암호화해 성공 |

8번이 게이트의 핵심 판정이고, 6·7번이 "강퇴와 재가입"입니다. 9·10번은 서버 선점 규칙이 진짜 PostgreSQL에서 맞는지 보는 것으로, API 단위 테스트의 동시성 항목과 겹치지만 종단에서도 한 번 봅니다.

### 3.2 다음 단계에 더할 것

| 단계 | 시나리오 | 게이트 근거 |
| --- | --- | --- |
| M1 | 백업 → 새 저장소에서 복구 코드로 복원 → 같은 상태. 백엔드가 생기기 전에는 코어의 가짜 서버로, 생긴 뒤에는 `make e2e`로. 시험 목록과 게이트 지표는 [M1 시험](qa/m1.md) | M1 "복구 코드로 새 기기 복원 100%" |

## 4. 결함 등급

결함은 영향(기밀성·무결성·가용성·데이터 손실)과 범위(모든 사용자, 한 그룹, 한 사람)와 우회 가능성으로 등급을 정합니다. 등급은 이슈 제목 앞에 `[S0]`처럼 붙입니다.

| 등급 | 정의 | 예 | 대응 |
| --- | --- | --- | --- |
| **S0 치명** | 종단간 암호화 약속이 깨지거나, 데이터가 사라지거나, 기기마다 다른 상태가 남음. 우회 불가 | 서버나 로그에 평문·키·토큰이 남음. 다른 그룹의 메시지가 보임. 같은 로그에서 다른 상태. 백업 복원 실패. 일정 유실. 인증 우회 | 다른 머지 중단. 원인을 고치는 PR이 먼저. 알파 이후에는 테스터에게 알림. 게이트 통과 불가 |
| **S1 심각** | 핵심 흐름(캘린더 입력, 동기화, 날짜 잡기, 채팅 전달)이 막히거나 자주 크래시. 우회가 없거나 어려움 | 동기화가 멈춤. 메시지 미전달. 투표가 닫히지 않음. 재현되는 크래시. 레이트 리밋이나 권한 검사가 빠짐 | 그 단계 안에 고침. 열린 S1이 있으면 게이트를 넘지 않음 |
| **S2 보통** | 기능이 틀리지만 우회할 수 있거나 범위가 좁음 | 드문 조건의 표시 오류, 재시도로 풀리는 오류, 불안정한(flaky) 테스트 | 다음 PR 묶음에서 고침. 게이트 판단에서 건수만 봄 |
| **S3 경미** | 문구, 간격, 색, 로그 메시지처럼 동작에 영향 없는 것 | 오타, 정렬, 비필수 경고 | 모아서 고침 |

규칙:
- **보안 결함은 S0 또는 S1입니다.** S2 이하로 두지 않습니다. 저장소가 공개이므로 재현 방법이 담긴 보안 결함은 공개 이슈에 쓰지 않고, GitHub의 비공개 취약점 보고(Security → Advisories)나 사용자와의 직접 채널로 다룹니다. 이슈에는 등급과 "보안"만 남깁니다.
- **크래시는 빈도로 나눕니다.** 재현되는 크래시는 S1, 재현되지 않는 크래시는 S2로 두고 게이트 지표(크래시 없는 세션 99.5%)로 봅니다.
- **의존성 권고는 [의존성 취약점 검사](security/dependencies.md) 3장**의 기준으로 등급을 매깁니다. 취약한 코드 경로를 우리가 쓰면 S1, 쓰지 않으면 S2(기록만)입니다.
- **등급이 애매하면 높은 쪽으로** 두고, 분석한 뒤 내립니다.

## 5. "녹색이어야 머지" 규칙

### 5.1 지금 걸려 있는 것

2026-10-25에 저장소 설정과 워크플로에서 확인한 내용입니다.

| 어디 | 무엇 |
| --- | --- |
| 룰셋 `main`(active, 우회 없음) | 삭제 금지, 강제 푸시 금지. PR 필수: squash 머지만, 리뷰 스레드 모두 해결, 필수 승인 수 0, 푸시 시 승인 무효화 없음. 필수 상태 검사 `ci-ok`, 최신 `main` 반영 요구(strict) 없음 |
| `.github/workflows/ci.yml` | `changes`가 바뀐 파트를 고르고, 파트 워크플로를 `workflow_call`로 부름. `lint`(actionlint, shellcheck)는 항상. `ci-ok`는 `needs` 중 실패·취소가 있으면 실패, 건너뛴 파트는 통과로 침. `main`에 푸시되면 모든 파트를 돎 |
| 리뷰 봇 | Codex(`chatgpt-codex-connector[bot]`)가 PR마다 리뷰. 스레드 해결 필수 규칙이 봇 지적을 처리하게 함 |
| Dependabot | 주 1회 생태계별 묶음 PR(`.github/dependabot.yml`). 같은 `ci-ok`를 거침 |
| 머지 방식 | 저장소 설정은 세 방식을 모두 허용하지만 룰셋이 squash만 남김 |

### 5.2 규칙

[CLAUDE.md](../CLAUDE.md) "여러 세션이 함께 일할 때"의 머지 조건을 QA 관점에서 풉니다.

1. **`ci-ok`가 녹색이어야 머지합니다.** 파트가 건너뛰어진 녹색도 녹색입니다. 다만 바뀐 파일이 그 파트 경로인데 건너뛰었다면 `scripts/ci/changed-parts.sh`의 규칙이 틀린 것이므로 먼저 고칩니다.
2. **빨간 검사를 녹색으로 만드는 방법은 원인을 고치는 것뿐입니다.** 테스트를 끄거나 격리하거나 `#[ignore]`로 돌리지 않습니다. 취약점 검사 예외(`deny.toml`의 `ignore`, `.trivyignore`)는 이유와 다시 볼 조건을 적어야 합니다([의존성 취약점 검사](security/dependencies.md) 3장).
3. **불안정한 테스트는 결함입니다.** 같은 커밋에서 한 번 실패하고 재실행에서 통과하면 S2 이슈를 열고, 두 번 실패하면 진짜 실패로 봅니다. 재실행은 한 번만 합니다.
4. **리뷰 봇의 지적은 고치거나 답합니다.** 고치지 않을 때는 이유를 답한 뒤 스레드를 해결합니다. 보안 지적은 사용자가 결정할 때까지 열어 둡니다.
5. **`main`이 빨개지면 다른 머지를 멈춥니다.** `main` 푸시 CI는 모든 파트를 돌리므로 PR에서 안 보인 문제가 여기서 드러납니다. 고치는 PR 또는 되돌리는 PR이 먼저 들어가고, 그동안 다른 PR은 `main`을 합친 뒤 다시 녹색을 확인합니다.
6. **`docs/`를 바꾸는 PR은 사용자의 확인을 받은 뒤 머지합니다.** 문서는 사용자가 확정합니다.
7. **공통 계약을 바꾸는 PR은 `docs/parts/protocol.md`와 `core/vectors/`를 먼저 바꿉니다.** 벡터가 바뀌면 `api`·`gateway`가 함께 돌아서 다른 파트의 파서가 깨지는지 같은 PR에서 드러납니다.
8. **Dependabot PR도 같은 규칙입니다.** `ci-ok` 녹색이면 머지하고, 빨간 것은 닫지 말고 원인을 적은 뒤 둡니다. 보안 수정이 ignore 규칙에 걸려 PR이 오지 않으면 손으로 올립니다(`build(<part>): ...`).
9. **비밀값이 생긴 뒤에도 `pull_request_target`은 쓰지 않습니다.** 저장소가 공개라 포크 PR이 들어올 수 있습니다. 지금은 CI에 비밀값이 없고, 배포 비밀값은 `main` 푸시나 수동 실행 워크플로에만 둡니다.
10. **게이트 판정은 QA가 합니다.** 게이트마다 (1) 파트 완료 조건의 테스트가 이름으로 존재하고 `main`에서 녹색인지, (2) 3장 시나리오가 `make e2e`에서 통과하는지, (3) 열린 S0·S1이 없는지를 확인해 사용자에게 보고합니다.

### 5.3 빈틈과 제안

| # | 빈틈 | 영향 | 제안 | 결정 |
| --- | --- | --- | --- | --- |
| 1 | 필수 검사가 최신 `main` 반영을 요구하지 않음(strict 아님) | 각각 녹색인 두 PR을 합치면 `main`이 빨개질 수 있음. `main` 푸시 CI가 잡지만 막지는 못함 | 지금은 유지하고 5.2 규칙 5로 다룸. strict로 바꾸면 머지마다 다른 PR의 검사가 무효가 되어 macOS 러너 분이 늘어남. 세션이 늘어 충돌이 잦아지면 strict로 바꿈 | 사용자 |
| 2 | `ios.yml`·`android.yml`이 `ci.yml`과 `ci-ok`에 없음 | 지금 `apps/`를 바꾸는 PR은 `lint`만 거쳐 머지됨 | 각 앱 파트가 첫 PR에서 [CLAUDE.md](../CLAUDE.md) "CI에 파트 붙이기" 절차를 따름. 그 전에는 `apps/` 변경을 머지하지 않음 | 해결(M0): `ios.yml`·`android.yml`이 `ci-ok`에 들어감 |

| 4 | 필수 승인 수 0 | 사람 리뷰 없이 머지 가능 | 1인 프로젝트이고 봇 리뷰 스레드 해결이 필수이므로 유지. 사용자가 머지 버튼을 누르는 것이 승인 | 유지 |
